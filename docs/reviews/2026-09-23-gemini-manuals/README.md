## スクリプトのテストで分かったこと

### 本文抽出で文脈が抜ける場合がある

`extract_blocks()` の対象には、単独の `strong` や `pre` が含まれません。今回の注意書き見出しは運営8個・開発5個、手順の見出しは運営21個・開発15個あり、これらは文章チェックの入力に含まれていませんでした。特に練習例の削除指摘には、この文脈欠落が影響したと考えられます。

また、抽出されたテキストにはHTML整形用の改行・空白が残ります。文章チェックの「改行」は、そのままブラウザー上の強制改行を意味しません。

### 全ページ撮影と遅延読み込みは別の処理

初回の運営手順書では13画像中10画像が撮影直前に未読込でした。`networkidle` と500ms待機だけでは、画面外の `loading="lazy"` 画像は読み込まれません。本戦表について、初回撮影画像は空白、スクロール後は正常表示になることを比較しました。

今回はオフラインでも使う静的手順書で、スクリーンショットはすでにHTML内にあります。手順書側の遅延読み込みを外し、全ページ撮影・印刷でも図を利用しやすくしました。汎用チェッカーとして使う場合は、全ページをスクロールして画像の読み込みを待つ処理も検討できます。

### 縦長の画像では誤読も起きる

初回の送信画像は運営2,880 × 38,180px、開発2,880 × 24,496pxでした。Geminiは「2戦」を「2敗」、`pnpm@9.12.0` を別のバージョン、画像更新スクリプト名を存在しない名前として引用しています。長い画像1枚の判定だけで本文やコマンドを変更しないことにしました。章単位の分割撮影は、チェッカーの改善候補です。

PCでは20,000pxの高さ上限内に収まりましたが、修正後の運営手順書は390px幅で21,544pxあります。スマートフォン条件で既定の全ページ撮影をすると末尾が対象外になるため、高さ上限や分割を明示する必要があります。

### API制限と指摘検出を区別する

再確認の同時実行では、無料枠のリクエスト制限（HTTP 429、limit 5）に当たりました。スクリプト内の再試行でも解消せず、サーバーが示した待機時間を過ぎてから運営手順書だけを再実行しましたが、今度はlimit 20のHTTP 429で終了しました。エラー文だけでは制限の集計期間を確定できないため、それ以上の再試行やモデル・課金設定の変更は行っていません。

APIエラー時も終了コードは1ですが、指摘検出時と違って結果JSONは出力されません。文章・体裁の両方が終わってから出力するため、途中まで成功したチェックもJSONには残らない構成です。自動実行では標準エラーとJSONの有無も確認する必要があります。
